## 1. Where to Fetch the Real-World Railway Blueprints
Instead of manually drawing tracks, we can pull actual, hyper-accurate railway lines and station coordinates for Bangalore.

**The Solution: OpenStreetMap (Overpass Turbo)**
We can extract real geographical data (GeoJSON) from OpenStreetMap.
1. Go to **overpass-turbo.eu** and center the map on Bangalore.
2. Run a query for: `way["railway"="rail"];` and `node["railway"="station"];`.
3. Export it as a `GeoJSON` file.
4. We can load this exact GeoJSON file directly into our frontend Map component (like Mapbox, Leaflet, or Google Maps) so the tracks follow real-world physical paths!

## 2. Geographical Scope: What Areas to Cover?

We need to decide how large of an area the demo will cover. Here are 3 options:

### Option A: The "Urban Core" (Recommended for Demo Stability)
- **Coverage:** Only within Bangalore city limits.
- **Key Stations:** KSR Bengaluru (Majestic), Yesvantpur Junction (YPR), Bengaluru Cantonment (BNC), and Krishnarajapuram (KJM).
- **Scale:** ~50 km of track. 
- **Data Points Generated:** **~5,000 components** (1 component every 10 meters).
- **Pros:** Keeps the map zoomed-in, dense, and visually busy without causing the browser to lag during rendering.

### Option B: The "Regional Starburst" (45km Radius - Chosen Scope)
- **Coverage:** Bangalore Regional core, radiating outward in a perfect starburst pattern in all directions for approximately 45 kilometers.
- **Key Corridors:** Covers all major suburban and regional tracks extending from the center out to the 45km perimeter.
- **Scale:** ~150 km of track.
- **Data Points Generated:** **~2,000 components** (This is the visual sweet spot. It spaces the dots out by ~135 meters, ensuring they look like distinct glowing nodes rather than a solid, cluttered line, while still looking incredibly rich and data-heavy for the judges).
- **Pros:** Shows the system handles inter-state/regional stretches. Looks very impressive to judges.

### Option C: The "State-Wide" Network (Overkill)
- **Coverage:** All of South Western Railway (Karnataka).
- **Scale:** ~3,000+ km of track.
- **Data Points Generated:** **300,000+ components**.
- **Pros/Cons:** Too heavy. Rendering 300k points on a web browser map will likely freeze the UI unless we use complex clustering algorithms.

> **My Suggestion:** Go with **Option B (Regional Corridors)**. 20,000 data points is the sweet spot. It's massive enough to impress the judges ("Look at all this data!"), but small enough that a standard React map component can cluster and render it smoothly.

## 3. The Dataset Breakdown

If we choose Option B (~20,000 components), here is exactly how we divide the data sets for the pitch:

### Dataset 1: The "Historical Baseload" (19,950 components)
- Generated by our procedural script.
- Saved as a static JSON file or loaded into a SQLite DB.
- Fetched via `GET /api/admin/dashboard/map` the instant the app loads.
- Contains the "Braking Zone" hotspots (red alerts near Yesvantpur and Majestic) to make the map look intelligently active.

### Dataset 2: The "Live Action Stream" (50 components)
- Held back from the initial map load.
- Delivered dynamically via WebSocket or a `/live-stream` endpoint when you press the "Start Demo" button.
- These are the components that *actively degrade* from Green to Red while the judges are watching, triggering the dispatch alerts to the Field Engineer app.

## 4. Key UX/UI & Performance Enhancements

### 1. Mapbox WebGL Rendering (Frontend)
To prevent the browser from crashing with 3,000 components, the map must use **Mapbox WebGL Layers** (like `Circle Layer`) rather than standard React components. This offloads rendering to the GPU, keeping the map silky smooth.

### 2. The Predictive Time Slider (The Killer Feature)
A timeline slider will be added to the frontend. Sliding it forward requests future predictions from the backend. 
- **Math Tweak:** Since age is usually calculated in years, dragging the slider 12-24 months forward needs to artificially boost the "Age Weight" heavily so the components visibly degrade (turn yellow/red) without completely destroying the network.

### 3. Future Feature: Demo Fail-Safe
To combat poor hackathon Wi-Fi, the backend will feature a Gemini fallback mode. If the API fails, a mock response is instantly returned.

## 5. The Final 12-Sector Map (Locked Definition)

After review, 6 sectors was too coarse for a 45km radius covering real Bangalore railway geography. The final scope uses **12 named sectors** derived from actual South Western Railway (SWR) junction names and corridor directions.

### The 12 Sectors

| # | Sector | Type | Real-World Node |
|---|---|---|---|
| 1 | Bangalore Central | Inner Core | KSR Bengaluru, BNC, City Railway |
| 2 | Yeshwantpur Zone | Inner Hub | YPR Junction (major interchange) |
| 3 | Krishnarajapuram Zone | Inner Hub | KJM Junction (eastern node) |
| 4 | Yelahanka Corridor | North | Yelahanka, Doddaballapur direction |
| 5 | Tumkur Corridor | Northwest | Nelamangala, Tumkur direction |
| 6 | Whitefield Corridor | East | IT hub suburban rail line |
| 7 | Bangarapet Corridor | Far East | Bangarapet, Kolar direction |
| 8 | Electronic City Corridor | Southeast | Carmelaram, Heelalige, EC |
| 9 | Hosur Corridor | South | Attibele, Hosur direction |
| 10 | Kengeri Zone | SW Inner | Kengeri station hub |
| 11 | Mysore Corridor | West-Southwest | Ramanagara, Mysore direction |
| 12 | Devanahalli Corridor | Far North | Devanahalli, Airport line |

> **The bounding box coordinates for all 12 sectors are defined identically in three places:**
> 1. `backend/scripts/generateData.js` — used to tag each component
> 2. `backend/docs/contracts.md` — the API contract reference
> 3. `frontend/src/constants/sectors.js` — used to render map polygons
>
> **These three must always stay in sync. Never change one without updating the others.**
