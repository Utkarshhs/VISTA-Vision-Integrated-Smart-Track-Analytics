# Master Technical Specification: RailTrack-AI Simulation

This document provides a comprehensive blueprint for building the **RailTrack-AI** frontend simulation. RailTrack-AI is an intelligent predictive maintenance platform designed to modernize railway track infrastructure management through hierarchical dispatching, AI-augmented health scoring, and offline-first data resilience.

---

## 1. Project Vision & Core USP
The primary challenge this project solves is the **"Connectivity Gap"** in remote railway sectors. The system allows field workers to operate in 100% offline environments, utilizing pre-downloaded predictive datasets and local sensor capture, syncing only when back in a network zone.

## 2. Deployment Strategy: Hybrid Model
The project follows a tiered deployment architecture to cater to different operational environments:

### PHASE 1: Centralized Web Dashboard (CURRENT FOCUS)
- **Target Audience:** Regional Controllers (Gov) and Hub Supervisors.
- **Environment:** Desktop-first, optimized for office "War Rooms" and large displays.
- **Core Goal:** Sector-wide situational awareness, predictive mapping, and dispatch orchestration.

### PHASE 2: Native Field App (FUTURE - DO NOT IMPLEMENT)
- **Target Audience:** Field Engineers on track-side duty.
- **Environment:** Mobile-first, optimized for offline use, camera access, and rugged field conditions.
- **Constraint:** **DO NOT START DEVELOPMENT** on the mobile application until explicitly confirmed by the user.

## 3. Hierarchical User Roles & Workflow
The application must support three distinct views (Role-Based Access Control simulation) to demonstrate the maintenance lifecycle:

### A. Regional Controller (The "Urban Rail Inspector")
- **Jurisdiction:** City-wide (e.g., Bangalore Sector).
- **Function:** Receives high-level "Predictive Flags" generated by the TensorFlow model.
- **Action:** Analyzes the sector-wide risk map and dispatches "Maintenance Alerts" to specific local hubs.

### B. Local Hub Supervisor (The "Station Lead")
- **Jurisdiction:** Station-specific (e.g., Majestic Hub, Yeshwantpur Hub).
- **Function:** Receives dispatches from the Regional Controller.
- **Action:** Manages a pool of field engineers and assigns specific track components to them for physical inspection.

### C. Field Engineer (The "Ground Inspector")
- **Jurisdiction:** On-site (Mobile View).
- **Function:** Performs physical verification of flagged components.
- **Action:** Captures photos, views vibration data, and triggers the **Gemini Vision API** to certify health or confirm replacement.

---

## 4. Cross-Platform Data Synchronization
The Web Dashboard and the Field Application are inherently interconnected through a **Centralized Cloud Database**.

- **Upstream Sync:** When a Regional Controller dispatches an alert via the **Web Dashboard**, it is instantly pushed to the assigned Field Engineer's **Mobile Application** (cached for offline use).
- **Downstream Sync:** When a Field Engineer completes an inspection or repair, the **Gemini-certified report** is synced back from the mobile app to the central server, updating the Controller's dashboard in real-time.
- **Single Source of Truth:** This ensures that the Government (Regional Controller) always has an up-to-the-minute view of the entire sector's integrity.

## 5. Data & AI Architecture

### Layer 1: Baseline Dataset (Manual Log)
The fundamental data structure for every track component:
```json
{
  "component_id": "TRK-BNG-MJ-001",
  "type": "ERC Clip",
  "age_months": 48,
  "last_inspection": "2024-01-15",
  "location": "12.9234, 77.5021 (Majestic West)"
}
```

### Layer 2: AI Augmentation (Stress Factors)
The **TensorFlow Predictive Model** (simulated) enhances Layer 1 by applying environmental multipliers:
- **Load Stress:** Average Tonnage (GMT) handled by the rail.
- **Rainfall Index:** Corrosion factor (0.0 - 1.0).
- **Thermal Gradient:** Heat expansion/contraction cycles.

### The Predictive Output: CII Score
The **Component Integrity Index (CII)** is a 0-100 score calculated as:
`CII = 100 - (Age_Factor + (Load * 1.5) + (Weather_Impact * 2.0))`

## 4. Component Integrity Index (CII) Protocols

| CII Range | Category | Color | Industry Action Required |
| :--- | :--- | :--- | :--- |
| **0 - 30** | **CRITICAL** | **Ruby Red** | **Emergency:** Immediate dispatch. Possible Temporary Speed Restriction (TSR). |

## 5. Gemini API: Vision & Reasoning Strategy
The **Gemini API** acts as the "Autonomous Inspector." It performs three critical functions via multi-modal prompting:

1.  **Vision Verification:** Detects physical defects (cracks, rust, displacement) in uploaded photos.
2.  **Temporal Delta:** Compares the *Current Photo* against a *Historical Reference* to calculate the **Rate of Decay**.
3.  **Critical Override:** If Gemini detects a structural crack visually, it can manually force a CII score to **<30 (CRITICAL)**, overriding the mathematical prediction.
4.  **Reporting:** Generates a professional, text-based "Maintenance Certification" for the database.

## 6. Technical Implementation Details (Frontend Simulation)

### Design System: "Dark Enterprise"
- **Background:** Charcoal/Deep Space (`#0a0b10`).
- **Surface:** Glassmorphic panels (`rgba(255, 255, 255, 0.05)` with blur).
- **Typography:** `Inter` (Sans) for UI, `Orbitron` (Futuristic) for IDs and Statuses.
- **Feedback:** Pulse animations for Critical components; Scan-line loaders for AI processing.

### Simulation Mechanisms
- **Offline Mode:** A state toggle that prevents "Gemini Analysis" and "Syncing" until toggled back to Online.
- **AI Processing:** Simulated delays (2-4 seconds) with progressive status updates (e.g., "Extracting features...", "Reasoning with Gemini...").
- **Human-in-the-Loop:** A "Truth Check" button for engineers to disagree with the AI, which logs a "Calibration Event."
